# Contributing guidelines

Contributions are welcome from anyone wanting to help improve the plugin.

When doing so, please follow the following steps:

1. Create an issue describing the change you would like and wait for feedback.
2. Once the change is agreed, feel free to raise a PR which makes the change.
3. The PR should stay in a draft state until it is ready for review and the build & test check is green.
4. Once a review of the PR has started (as indicated by a comment on the PR), no further changes should be made until the review is complete.
5. Once the PR is approved, it will be merged and a new release made.

Please keep PRs to a manageable size - excessively large PRs are likely to spend a long time waiting for review. Keep descriptions and comments courteous and concise.

All changes must have appropriate logging using appropriate log levels. Code comments are encouraged to explain _why_ something it being done, or explain in simple terms _what_ is being done if the code is necessarily complex or convoluted.

## LLM requirements

Contributions that make use of LLMs for writing code are welcome, with the following caveats:

- All issue descriptions, PR descriptions and comments _must_ be human authored.
- All code submitted must be perfectly understood by the person submitting the PR. If, when questioned, the submitter is unable to explain why something has been done in a particular way, the PR will be closed.
- If a PR enters into a state of "comment ping pong" indicative of LLMs failing to make appropriate changes, the PR will be closed.

Repeated failures to comply with the above requirements may result in blocking further contributions from the individual.
